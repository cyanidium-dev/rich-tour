# План архитектурного рефакторинга Rich Tour

Этот план выполняется на текущем состоянии репозитория и не зависит от
незакрытых этапов `DEPENDENCY_UPGRADE_PLAN.md`. Он предназначен для работы по
частям: **одна новая сессия — один этап**. Создание этого документа не означает,
что этап 0 начат или выполнен.

## Правила для каждой сессии

1. Прочитать этот документ целиком и выполнить `git status --short`. Сохранить
   все существующие изменения пользователя; не очищать рабочее дерево ради этапа.
2. Выполнить только указанный этап и остановиться. Не переходить к следующему
   этапу автоматически и не отмечать пункты плана обновления зависимостей.
3. Сохранять внешний вид, пользовательские сценарии, URL, форматы запросов и
   ответов API. Формы без действующей серверной отправки не подключать к новому
   backend в рамках рефакторинга.
4. Для новых зависимостей использовать npm и обновлять `package.json` вместе с
   `package-lock.json`. Не обновлять попутно остальные пакеты.
5. Для каждого затронутого компонента проверять, нужна ли ему клиентская
   граница и какие модули попадут в его клиентский граф импортов. В отчёте по
   этапу кратко указать изменённые Server/Client Components и причины решений.
6. После каждого этапа выполнять `npm run typecheck`, `npm run lint`,
   `npm run build` и тесты, относящиеся к изменению. Начиная с этапа 0, запускать
   также `npm run test`. Для затронутых пользовательских сценариев выполнять
   указанный smoke-тест. Если обязательная проверка не прошла, чекбокс этапа
   остаётся открытым; недоступные внешние проверки и их причины записывать в
   отчёт, не объявляя их пройденными.
7. В конце сессии сообщить изменённые области, результаты проверок, состояние
   Server/Client границ и оставшиеся ограничения. Отмечать этап выполненным
   только после его критериев завершения.

Не запускать деплой, миграции или очистку рабочих данных Sanity/CRM. Скрипты
с флагами `--apply` не относятся к этому плану.

## Целевая архитектура

```text
src/
  app/          маршруты Next, layout, providers, тонкие API-обработчики
  widgets/      составные блоки страниц: header, footer, tour-details, orders-workspace
  features/     действия: booking, tour-search, auth, profile-edit, order-filters
  entities/     предметные модели: tour, order, user, review и другие при повторном использовании
  shared/
    api/        низкоуровневые клиенты внешних систем
    ui/         общие элементы интерфейса и поля форм
    lib/        функции без привязки к предметной области
    config/     общие настройки и константы
    styles/     токены и общие стили
```

- Зависимости направлены вниз: `app → widgets → features → entities → shared`.
  Слой может импортировать любой нижележащий слой, но не вышележащий. Срезы
  одного слоя не импортируют внутренние файлы друг друга.
- У каждого среза есть публичный `index.ts` для безопасных общих экспортов и,
  когда нужен серверный код, отдельный `server.ts`. Внутренние части размещаются
  в `ui`, `model`, `api`, `lib` только при наличии соответствующего кода.
  Серверные модули защищаются `server-only`; клиентский код не импортирует
  серверные клиенты, секреты и серверные точки входа.
- `app` выполняет роль слоя страниц Next; отдельный FSD-слой `pages` не нужен.
  Небольшие элементы, используемые только одним маршрутом, остаются в его
  `_components`. Крупные составные блоки выносятся в `widgets`.
- Типы, запросы Sanity и преобразования туров принадлежат `entities/tour`;
  отправка брони — `features/booking`; модель и преобразование заказов —
  `entities/order`, их экран — `widgets/orders-workspace`, фильтры —
  `features/order-filters`. Низкоуровневые клиенты Sanity/CRM принадлежат
  `shared/api`. Маршруты `app/api` разбирают запрос и вызывают серверную логику
  соответствующего среза, сохраняя нынешний HTTP-контракт.

### Server и Client Components

Server Component — исходный вариант даже для компонента без загрузки данных.
`"use client"` нужен для клиентского состояния, обработчиков событий, эффектов,
браузерных API, контекста или библиотек, которым требуется клиентский runtime.
`Link`, статическая разметка и CSS сами по себе не требуют клиентской границы.

Проверять не только наличие директивы, но и всё дерево импортов из неё. Если
интерактивна часть блока, серверный родитель собирает статическую разметку и
передаёт сериализуемые данные клиентскому компоненту. Клиентские провайдеры
должны охватывать только необходимую область; переданные им серверные `children`
могут оставаться серверными. Анимации, формы и интерактивные элементы сохраняют
клиентский runtime, когда он действительно нужен. Не ставить цель удалить
фиксированное число директив: цель — корректные и узкие границы.
