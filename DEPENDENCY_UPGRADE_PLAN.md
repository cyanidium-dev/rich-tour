- В `package.json` зафиксирован `engines.node = 24.x`.
- В `.nvmrc` указано `24`.

- Dataset `production` используется для публичного контента, а `users-production` — отдельный публичный dataset для зашифрованных пользовательских записей.
- Публичный `users-production` является осознанным компромиссом и не эквивалентен приватному хранилищу: структура документов, технические статусы и шифротекст доступны для чтения извне.

- Не запускать deploy в Vercel и `sanity deploy` без отдельного явного подтверждения пользователя после завершения правок.
- Наполнение `users-production` уже выполнено, но переключение рабочей версии сайта и Studio считается отложенным до общей публикации.
- До публикации финальной версии и успешного production smoke-теста не запускать `users:cleanup:apply`: старые пользовательские документы в `production` должны оставаться доступными как откатная копия.
- Проверку рабочей авторизации, просмотр паролей в опубликованной Studio и окончательное закрытие этапа 0A выполнить в общей фазе публикации.

### Модель хранения

- Dataset `users-production` создаётся с visibility `public` только из-за ограничений Sanity Free.
- Документ содержит случайный `_id`, `_type`, версию формата, минимальные технические поля и зашифрованный payload.
- Payload шифруется AES-256-GCM с уникальным случайным IV для каждой записи и authenticated data, включающим `_id`, `_type` и версию формата.
- Нормализованный email/login индексируется только через HMAC-SHA-256. Исходный email/login в открытых полях отсутствует.
- Один 32-байтовый `USER_DATA_MASTER_KEY` хранится в `.env.local`, Vercel и отдельно передаётся только доверенным администраторам через защищённый канал; отдельные ключи шифрования и lookup выводятся из него через HKDF.
- Внутри зашифрованного payload сохраняется требуемая пара `password: {plain, hash}`. В открытых полях документа не должно быть ни исходного пароля, ни bcrypt-хэша.
- В Sanity Studio используется специальный read-only password viewer: после проверки роли он просит администратора вручную ввести master key, расшифровывает payload локально через Web Crypto и показывает пароль только по явному действию.
- Master key не встраивается в Studio bundle, не записывается в Sanity, localStorage/sessionStorage, логи или telemetry и очищается из памяти при закрытии/перезагрузке представления.
- В открытом виде допускаются только необходимые для cron несекретные поля: версия схемы, тип роли, статус CRM retry, число попыток и время следующей попытки. CRM ID и текст ошибки остаются зашифрованными.

### Действия

1. Создать публичный dataset:

   ```bash
   npx sanity@latest datasets create users-production --visibility public --project-id elggedkx
   ```

2. Добавить `SANITY_USERS_DATASET=users-production` и `USER_DATA_MASTER_KEY` в `.env.local`, `.env.example` и Vercel. Ключ не должен иметь префикс `NEXT_PUBLIC_`.
3. Реализовать совместимый формат шифрования для Node `crypto` и Web Crypto: фиксированная версия envelope, HKDF, AES-256-GCM, уникальный IV и authenticated data. Не добавлять криптографические зависимости без необходимости.
4. Создать типизированный server-only репозиторий пользователей. Остальной код не должен напрямую читать или записывать структуру зашифрованных Sanity-документов.
5. Перевести регистрацию, вход, смену пароля, чтение/изменение профиля, кабинеты и CRM-синхронизацию на новый репозиторий.
6. Для регистрации и смены email/login проверять уникальность по HMAC lookup. Использовать constant-time comparison там, где сравниваются секретные значения.
7. Добавить custom document view/input в Sanity Studio для пользовательских документов:
   - по умолчанию пароль скрыт и ciphertext не отображается как обычное редактируемое поле;
   - кнопка `Показать пароль` доступна только разрешённым ролям через `useCurrentUser`/`userHasRole`;
   - перед расшифровкой администратор вручную вводит master key, который хранится только в памяти компонента;
   - пароль автоматически скрывается по таймауту, при blur, закрытии документа и размонтировании компонента;
   - копирование требует отдельного явного действия и не пишет значение в console/telemetry;
   - изменение пароля выполняется контролируемым действием, которое одновременно обновляет `plain` и bcrypt `hash` внутри нового ciphertext.
8. Проверку роли в Studio считать только защитой от случайного просмотра, а не криптографической границей. Расшифровать данные может любой, у кого есть master key.
9. Перед переносом добавить раздельные команды:
   - `users:migrate:plan` — только чтение, проверка и отчёт;
   - `users:migrate:apply` — идемпотентное шифрование и копирование после явного подтверждения;
   - `users:cleanup:plan` — список старых открытых `agentUser`/`agencyUser` в `production`;
   - `users:cleanup:apply` — удаление старых открытых документов только после отдельного подтверждения и успешного smoke-теста.
10. Во время миграции переносить `{plain, hash}` только внутрь ciphertext. Если есть `plain`, но хэш отсутствует/невалиден, создать новый bcrypt-хэш; если есть только хэш, исходный пароль восстановить невозможно — пометить запись для смены пароля администратором или пользователем.
11. Сверить количество, ID, роли, связи агентства, CRM ID и статусы синхронизации до и после миграции. Не создавать тестовые дубли в CRM.
12. После переключения убедиться, что в `production` и `users-production` не осталось открытых email, телефонов, адресов, паролей, хэшей или CRM ID.
13. Проверить регистрацию, вход агента и агентства, смену пароля, профили, кабинеты, CRM retry, повреждённый ciphertext и запуск с неверным/отсутствующим master key.
14. В Studio проверить: доступ разрешённой роли, отсутствие кнопки у остальных ролей, неверный ключ, reveal/hide, автоочистку, копирование и согласованное обновление `{plain, hash}`.
15. Проверить отсутствие `USER_DATA_MASTER_KEY`, расшифрованных payload и персональных данных в client bundle, логах, source maps, localStorage и sessionStorage.
16. Выполнить `npm ci`, `typecheck`, `lint`, `build` и `npm audit --omit=dev`.

### Ограничения и принятый риск

- Публичный dataset позволяет скачать шифротекст и проводить офлайн-анализ; безопасность полностью зависит от стойкости и сохранности master key.
- Потеря master key означает потерю доступа к данным. Бесплатный план не даёт полноценной управляемой схемы резервирования ключа, поэтому владелец должен хранить отдельную защищённую копию ключа.
- Компрометация master key раскрывает весь dataset.
- Администратор, которому выдан master key, технически получает доступ ко всем расшифровываемым пользовательским данным и исходным паролям. Отозвать этот доступ можно только ротацией ключа и повторным шифрованием всех записей.
- Показ исходного пароля повышает риск утечки через экран, буфер обмена, вредоносное расширение браузера или скомпрометированное устройство администратора.
- Sanity CORS, скрытые имена полей и сложные GROQ-запросы не считаются защитой.

### Не делать

- Не хранить `password.plain`, bcrypt-хэш или персональные данные вне зашифрованного payload.
- Не использовать детерминированное шифрование вместо HMAC lookup.
- Не выводить расшифрованные данные или ключи в логи и отчёты миграции.
- Не встраивать master key в Studio, `.env` Studio-сборки или любой `SANITY_STUDIO_*`/публичный env.
- Не удалять исходные документы до полной сверки и отдельного подтверждения cleanup apply.
- Не публиковать текущую промежуточную версию сайта или Sanity Studio; deployment отложен до завершения запланированных правок и отдельного подтверждения пользователя.
- Не начинать major-обновления Next/React/UI в этом этапе.
